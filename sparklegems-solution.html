Step 0 · Unnormalised form

One table trying to be five things at once

SparkleGems records every sale in a single sheet that mixes order, customer, product and designer facts. Before splitting anything, name the exact rules it breaks.

Goal One fact, one place. Five orders, eight jewellery pieces, four customers, two designers — all crammed into eleven columns.

Reading note: the Quantity column in the spreadsheet

Excel silently converted the multi-value quantity cells into dates (serials 45658 and 45689). The cells carry the number format d, m, so 45658 renders as 1, 1 and 45689 as 1, 2. Those are the quantities used throughout this solution.

Which rules are broken

  1. Non-atomic cells. Ring - Diamond, Necklace - Gold is a list, and Quantity and Price are parallel lists matched only by position. Nothing stops the lists from falling out of step.
  2. Two facts in one column. ItemName, Material mixes what the piece is with what it is made of.
  3. Repeating customer block. Asha Mehta's name, phone and city are stored once per order, not once per customer.
  4. Repeating designer block. Priya Shah's phone number is copied into three different rows.

The anomalies this causes

  1. Insert anomaly. A newly hired designer, or a new piece that has not sold yet, cannot be recorded — there is no order to hang it on.
  2. Update anomaly. Asha Mehta moves from Mumbai to Nashik: every one of her order rows must change, and any row missed leaves the database contradicting itself.
  3. Delete anomaly. Cancel order O1004 and the only record of Necklace - Diamond and its ₹80,000 price disappears with it.
  4. No safe key. OrderID cannot identify a row while one row holds two different jewellery pieces.

Step 1 · First Normal Form

1NF: one value per cell, one row per order line

Split the item list into separate rows, split ItemName, Material into two columns, and pair each quantity and price with its own piece. Nothing is moved to a new table yet.

Rule applied 1NF = atomic cells + no repeating groups + every row uniquely identifiable. Primary key becomes the composite (OrderID, ItemID).

What changed and why

  1. ItemName, Material became two columns — one column, one kind of fact.
  2. Each item in a list got its own row, and the positional Quantity / Price lists were unpacked alongside it.
  3. ItemID (P01–P08) was introduced so a piece can be referenced by key instead of by a text description.
  4. The key is now the composite (OrderID, ItemID): an order can hold many pieces, and a piece can appear in many orders.

Stated assumption

Price is read as the unit price of the piece, not the line total. Every (ItemName, Material) pair in the data carries exactly one price, which supports this reading. LineTotal = Quantity × Price is derived and is never stored.

Functional dependencies now visible

  • OrderID → OrderDate, CustomerID, DesignerName, DesignerPhone Only half the key is needed — a partial dependency.
  • CustomerID → CustomerName, CustomerPhone, CustomerAddress Reached through OrderID, so also transitive.
  • ItemID → ItemName, Material, Price The other half of the key — also partial.
  • DesignerName → DesignerPhone A non-key field determining another non-key field.
  • (OrderID, ItemID) → Quantity The only fact that genuinely needs the whole key.

Step 2 · Second Normal Form

2NF: every non-key fact must need the whole key

The key is (OrderID, ItemID). Anything determined by OrderID alone, or by ItemID alone, is a partial dependency and moves to its own relation.

Rule applied 2NF = 1NF + no partial dependency on part of a composite key. Only Quantity survives in the bridge table.

The partial dependencies being removed

  • OrderID → OrderDate, CustomerID, CustomerName, CustomerPhone, CustomerAddress, DesignerName, DesignerPhone Half of the key determines all of this → move to Order_Header.
  • ItemID → ItemName, Material, Price The other half of the key determines this → move to Item.
  • (OrderID, ItemID) → Quantity Needs both halves → stays in OrderItem.

Step 3 · Third Normal Form

3NF: non-key facts describe the key, not each other

Inside Order_Header two dependency chains are hiding. Break both, and each entity finally gets its own home.

Rule applied 3NF = 2NF + no transitive dependency among non-key fields. K → A → B means B belongs in A's table.

The transitive chains being broken

  • OrderID → CustomerID → CustomerName, CustomerPhone, CustomerAddress Customer details describe the customer, not the order → new Customer table.
  • OrderID → DesignerName → DesignerPhone The phone describes the designer, not the order → new Designer table, keyed by a surrogate DesignerID so the name is never used as an identifier.
  • OrderID → OrderDate, CustomerID, DesignerID What genuinely remains an order fact.

Anomalies removed

Update: Asha moves city → one row in Customer changes. Insert: a new designer or an unsold piece can be added with no order. Delete: cancelling O1004 removes one order and one order line; Necklace - Diamond stays in the catalogue.

Trap to avoid: the dependency that is not there

In this sample C001 is always handled by Priya Shah and C002 always by Mehul Jain, so it is tempting to write CustomerID → DesignerID and drop the designer from Orders. That is a coincidence of five rows, not a business rule — SparkleGems never promised a customer one permanent designer. A functional dependency must be guaranteed by the business, never inferred from a small sample.

Step 4 · Boyce-Codd Normal Form

BCNF: every determinant must be a candidate key

BCNF is a stricter re-test, not a new split. List every determinant in every 3NF relation and ask one question of each: does it identify a whole row?

Rule applied BCNF: for every non-trivial X → Y, X must be a superkey. 3NF forgives a determinant that is a prime attribute. BCNF forgives nothing.

Two details worth pausing on

  1. Item has two candidate keys. ItemID and (ItemName, Material) both identify a piece, so the UNIQUE (ItemName, Material) constraint is not decoration — it is what stops "Ring / Gold" being catalogued twice at two prices.
  2. Why DesignerID and not DesignerName. Keying Designer on the name assumes no two designers ever share a name. The moment a second Priya Shah is hired, DesignerName → DesignerPhone stops being a key dependency and the relation breaks BCNF. The surrogate key removes that risk permanently.

What a BCNF failure would have looked like

Hypothetical — not SparkleGems' actual rule. Suppose the business said "each designer works in exactly one material" and the designer were recorded per order line:

  • Key = (OrderID, ItemID)  ·  DesignerID → Material Material is a prime attribute, so 3NF would allow this. BCNF rejects it: DesignerID is a determinant but not a superkey.

The fix is the standard BCNF split: DesignerMaterial(DesignerID, Material) plus OrderLineDesign(OrderID, ItemID, DesignerID). Note the price of BCNF — the original FD (OrderID, ItemID) → Material can no longer be enforced inside a single table. BCNF is always lossless, but not always dependency-preserving; 3NF is both.

Step 5 · Deliverable

Final schema, DDL and the proof it is lossless

Five relations in BCNF, the constraints that keep them honest, and one query that rebuilds the original sales report exactly.

Result 1 table → 5 tables. Zero repeated facts. Customer · Designer · Orders · Item · OrderItem

Schema map

DDL — PostgreSQL / standard SQL

-- Final BCNF schema for SparkleGems

CREATE TABLE Customer (
  CustomerID      CHAR(4)      PRIMARY KEY,
  CustomerName    VARCHAR(60)  NOT NULL,
  CustomerPhone   VARCHAR(15)  NOT NULL UNIQUE,
  CustomerAddress VARCHAR(80)  NOT NULL
);

CREATE TABLE Designer (
  DesignerID    CHAR(3)     PRIMARY KEY,
  DesignerName  VARCHAR(60) NOT NULL,
  DesignerPhone VARCHAR(15) NOT NULL UNIQUE
);

CREATE TABLE Item (
  ItemID   CHAR(3)       PRIMARY KEY,
  ItemName VARCHAR(30)   NOT NULL,
  Material VARCHAR(30)   NOT NULL,
  Price    NUMERIC(10,2) NOT NULL CHECK (Price > 0),
  UNIQUE (ItemName, Material)   -- second candidate key
);

CREATE TABLE Orders (
  OrderID    CHAR(5) PRIMARY KEY,
  OrderDate  DATE    NOT NULL,
  CustomerID CHAR(4) NOT NULL REFERENCES Customer(CustomerID),
  DesignerID CHAR(3) NOT NULL REFERENCES Designer(DesignerID)
);

CREATE TABLE OrderItem (
  OrderID  CHAR(5) REFERENCES Orders(OrderID) ON DELETE CASCADE,
  ItemID   CHAR(3) REFERENCES Item(ItemID),
  Quantity INT     NOT NULL CHECK (Quantity > 0),
  PRIMARY KEY (OrderID, ItemID)
);

Proof: the join rebuilds the original report

Lossless 
SELECT o.OrderID, o.OrderDate,
       c.CustomerID, c.CustomerName, c.CustomerPhone, c.CustomerAddress,
       i.ItemName, i.Material, oi.Quantity, i.Price,
       oi.Quantity * i.Price AS LineTotal,
       d.DesignerName, d.DesignerPhone
FROM Orders o
JOIN Customer  c  ON c.CustomerID = o.CustomerID
JOIN Designer  d  ON d.DesignerID = o.DesignerID
JOIN OrderItem oi ON oi.OrderID   = o.OrderID
JOIN Item      i  ON i.ItemID     = oi.ItemID
ORDER BY o.OrderID, i.ItemID;

Eight rows out — the same eight order lines the 1NF table held, with no invented rows and none lost. Because every split was along a functional dependency whose determinant became the primary key of the new table, each join is guaranteed lossless.

Answer sheet in one line per stage

  1. UNF — SparkleGemsSales(OrderID, OrderDate, CustomerID, CustomerName, CustomerPhone, CustomerAddress, "ItemName, Material", Quantity, Price, DesignerName, DesignerPhone)
  2. 1NF — OrderLine(OrderID, ItemID, OrderDate, CustomerID, CustomerName, CustomerPhone, CustomerAddress, ItemName, Material, Quantity, Price, DesignerName, DesignerPhone)
  3. 2NF — Order_Header(OrderID, OrderDate, CustomerID, CustomerName, CustomerPhone, CustomerAddress, DesignerName, DesignerPhone)  +  Item(ItemID, ItemName, Material, Price)  +  OrderItem(OrderID, ItemID, Quantity)

  5. BCNF — unchanged; every determinant in the 3NF design is already a candidate key.
